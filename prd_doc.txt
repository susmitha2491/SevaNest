## Objective

Simplify the worker row-click experience in the Verification Executive's Workers Directory.

Currently, clicking a row opens an oversized, cluttered Worker Detail Modal containing multiple tabs, lifecycle stages, banners, and operational information.

Replace this row-click experience with a clean, focused **Worker Application Details** view. The Verification Executive should be able to review the applicant's details and make an authorized accept/reject decision.

**Implementation and testing only. Do not commit, push, merge, or deploy.**

## 1. Simplify the Row-Click Experience

Inspect `WorkersListPage.tsx`, `WorkerDetailModal.tsx`, and the existing verification dossier components.

When the user clicks a worker row:

- Open a clean, centered Worker Application Details modal.
- Do not open the existing multi-tab operational dossier for this action.
- Keep the modal appropriately sized, responsive, and easy to read.
- Use a simple header with the worker's name, application reference, current verification status, and a close button.
- Remove unnecessary lifecycle stepper cards, repeated status banners, redundant metadata, and unrelated operational controls from this simplified view.
- Keep the worker directory and its filters unchanged when the modal closes.

Do not delete the existing detailed dossier functionality. The Verification Queue and explicit dossier-inspection actions must continue to use their appropriate existing workflows.

## 2. Show Only Relevant Application Details

Organize the application into clear sections:

### A. Applicant Information
Display actual backend data when available:
- Worker ID and application reference.
- Full name.
- Contact information with existing privacy masking.
- Locality or service area.
- Applied service category and skills.
- Experience and relevant qualifications.
- Application submission date.
- Current verification status.

### B. Submitted Documents
- Show the available document types and actual backend-provided document statuses.
- Provide document inspection only when the required document ID and secure document-link API are available.
- Show honest loading, missing-document, and API error states.
- Do not fabricate document numbers, document statuses, or preview URLs.
- Keep document inspection separate from the accept/reject decision.

### C. Application Decision
Provide a clear decision section at the bottom of the modal.

Display **Accept Application** and **Reject Application** only when the authenticated Verification Executive has the necessary server-issued decision permission and the backend supports the corresponding operation.

## 3. Implement the Correct Acceptance Workflow

First inspect the approved business requirements, current verification workflow, RBAC permissions, and existing backend API contracts.

Distinguish between:
- Approving an individual KYC verification check.
- Completing the worker's overall verification.
- Accepting or approving the worker's application.
- Activating the worker for search and bookings.

These operations must not be treated as interchangeable.

The Verification Executive should be able to make the intended decision only if the documented business rules and backend permissions authorize it.

Before implementing a final application acceptance action, determine whether the existing backend supports a worker/application-level final decision. Do not assume that approving one document or check accepts the entire application.

If the backend supports only individual check approval:
- Keep those actions in the verification dossier.
- Do not label them as accepting the entire worker application.
- Document the missing application-level decision endpoint or contract for the backend team.

If the final acceptance endpoint or permission is missing:
- Do not simulate acceptance by changing frontend state.
- Do not fabricate an endpoint or introduce a new status.
- Record the exact backend requirement in `docs/sevanest-backend-integration-gap-register.md`.

Do not automatically activate a worker after acceptance unless the approved business rules explicitly require it.

## 4. Rejection Workflow

- Show a rejection confirmation dialog.
- Require the rejection reason and any remarks mandated by the existing approved rules and backend contract.
- Prevent accidental duplicate submissions.
- Display success only after the backend confirms the decision.
- Refresh the worker record and relevant list data after a successful response.
- Preserve the existing application status if the request fails.

Do not invent rejection reason codes. If approved codes are unavailable, document that dependency.

## 5. Role-Based Permissions

- Respect the authenticated user's server-issued permissions.
- Viewing an application must not automatically grant decision-making permissions.
- Do not bypass RBAC or add Super Admin privileges to the Verification Executive.
- Keep customer verification outside this workflow.
- Keep account activation separate from application acceptance.

## 6. Preserve Existing Actions

- Clicking a worker row opens the simplified Worker Application Details modal.
- `View Profile` may continue to open the existing detailed worker profile if that is its established behavior.
- `Review KYC` must continue to open the Verification Queue/dossier.
- Clicking action buttons must not trigger the row click handler.
- Preserve search, category, verification filters, sorting, and pagination when closing the modal.

## 7. Design Requirements

Use a clean, professional administrative layout:
- Compact modal header.
- Clearly labeled information sections.
- Minimal status badges.
- Readable spacing and typography.
- Responsive layout with a sensible maximum width and height.
- Scroll only within the modal body when necessary.
- Sticky header and footer when appropriate.
- Accept and Reject actions clearly separated at the bottom.
- Accessible keyboard navigation and visible focus indicators.

Avoid excessive cards, repeated banners, large empty areas, or unnecessary workflow stepper components.

## 8. Testing and Docker Validation

Add or update tests for:
- Row click opens the simplified application modal.
- Correct worker details are loaded using the real worker ID.
- Existing `View Profile` and `Review KYC` actions remain independent.
- Authorized decision actions appear only when permitted.
- Acceptance does not imply account activation.
- Rejection validation and backend failures are handled correctly.
- Missing application-level decision APIs are handled honestly.
- Closing the modal preserves directory filters and pagination.

Run:
- `npm run typecheck`
- `npm run lint`
- `npm run test`
- `npm run build`

Manual UI testing must use Docker only. Do not run `npm run dev`.

Rebuild `sevanest-admin-portal:latest`, recreate/update `sevanest-admin` with port mapping `8080:80`, and verify `http://localhost:8080/healthz`.

Test the new application view and its decision controls using authorized backend access where available. Clearly report anything blocked by missing backend credentials or endpoints.

4. Any missing backend contracts.

1. Product Overview & Executive Summary 
SevaNest is a proposed simple, trusted and scalable household workforce platform connecting customers with verified 
maids, drivers, cooks, babysitters, elderly-care helpers and house-cleaning workers. The platform supports recurring 
household employment as well as short-term service requirements. 
The product consists of a Customer Mobile App, Worker Mobile App and Web-based Admin Panel. The first production 
release is planned within four months (16 weeks), with parallel work across product design, mobile applications, 
backend, admin portal, integrations, testing and deployment. 
The core product principle is simplicity: customers should be able to find a suitable worker in a few steps, while workers 
should be able to register, verify identity, specify availability and receive job opportunities without navigating a complex 
interface.

1.1 Product Name Rationale 
"Seva" represents service/help, while "Nest" represents the home. The name is broad enough to include maids, drivers, 
cooks, caregivers and future home-service categories without restricting the brand to one role. 
Working product name: SevaNest. Trademark, company-name and domain availability must be verified before public 
launch. 
1.2 Product Goals 
 Make household staff discovery and hiring simple and structured. 
 Create a trusted worker-verification and customer-verification process. 
 Support recurring monthly employment as well as daily/hourly requirements. 
 Provide interview, booking, payment, attendance, rating and replacement workflows. 
 Give operations teams complete control through an admin dashboard. 
 Build a scalable technology base for multi-city expansion.
