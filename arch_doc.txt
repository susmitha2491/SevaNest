Presentation. Queues, detail screens and forms with plain status
labels. No API calls and no business rules here.
Domain. The rules: entities and use cases such as
ReviewVeriﬁcation, ChangeBookingStatus and IssueRefund, plus
permission policies.
Data. Talks to the backend and to signed document links; turns API
errors into domain failures.
Core / Shared. API client, session, RBAC helpers, design system
and logging used by every feature.
Backend. The server is the source of truth for status, permissions,
payments and the audit trail.
Calls ﬂow downward. The Data layer implements Domain interfaces; the Domain layer never depends on React or HTTP.
One React codebase serves every admin role. Every backend call goes through the Admin API Gateway over HTTPS with token-based sessions. What
a user can see is decided by permissions issued by the server, not by role names hard-coded in the UI. Only signed document links, map tiles and error reports
are reached directly from the browser.

RULES IN THE PORTAL
Why this design. The PRD says a worker is never presented as fully veriﬁed until
checks are approved by an authorised user, and that every change stays auditable.

Repository interfaces live in the Domain layer; implementations live in the Data layer. API responses
are mapped from DTOs to domain entities, so screens never see raw API shapes.
Server data lives in the query cache; local UI state stays small.
Filters, sort and page live in the URL.
After a change, related queries are refetched so lists never show stale status.
The server is the source of truth for status, permissions and payments.
Why version checks. Several admins work at once (the PRD calls for role-based concurrent operations). A version check on every edit means a stale save is refused with a clear message, instead of silently overwriting a colleague's
change.
